GameEngine CLI Manual

The GameEngine CLI controls and inspects a running editor, automates editor UI and scene operations, captures rendering diagnostics, authors ECS and game-graph source, and runs engine build and test workflows.

There are two equivalent command-line entry points:

  • node Tools/ai/ge.mjs is the development launcher. It rebuilds the TypeScript CLI when mcp/src is newer than mcp/dist.
  • gameenginecli is the standalone executable. It embeds Node and does not require a Node installation at runtime.

Both use the same registry as the GameEngine MCP server. A typed tool added to mcp/src/tools/ therefore appears in MCP, ge, and gameenginecli together.

In this manual, ge means either entry point. Replace it with the command appropriate for the installation:

node Tools/ai/ge.mjs get_editor_state
gameenginecli get_editor_state

Requirements

The development launcher requires:

  • Node.js 20 or later
  • npm
  • a GameEngine checkout

Most commands also require a running editor with its debug server listening. The default address is 127.0.0.1:9999.

Host-side commands do not require a running editor:

  • build_engine
  • run_tests
  • launch_editor
  • editor_full_cycle
  • shutdown_editor
  • ECS source-authoring commands
  • game-graph file and code-authoring commands
  • list_debug_methods

Some host-side operations still require a configured build tree, compiler, CMake, or project files appropriate to the operation.

Installation and startup

Development launcher

Install the MCP/CLI dependencies once:

npm --prefix mcp ci

The launcher checks timestamps before every invocation and runs the TypeScript build when necessary:

node Tools/ai/ge.mjs --help

The first invocation also installs dependencies if mcp/node_modules is absent. Build messages go to stderr, leaving stdout safe for JSON consumers.

The following environment variables control this behavior:

VariableEffect
GE_CLI_NO_BUILD=1Skip the source-versus-output staleness check.
GE_CLI_FORCE_BUILD=1Rebuild before the invocation.

Standalone executable

Build the native wrapper through CMake:

cmake --build build/<preset> --config <configuration> --target GameEngineCli

The result is staged under the build tree’s bin/<configuration> directory as gameenginecli or gameenginecli.exe. The executable contains the same JavaScript and tool registry as the development CLI at the time it was built. It does not perform the development launcher’s staleness check.

The standalone executable is platform-specific and cannot be cross-packaged through Node SEA. Build it separately on each target platform.

Start or connect to the editor

To launch an editor and wait until its debug server is ready:

ge launch_editor
ge wait_for_editor
ge get_editor_state

For a non-default editor port:

export GE_EDITOR_DEBUG_PORT=11001
ge launch_editor
ge wait_for_editor
ge get_editor_state

Set the environment variable when launching because the child editor inherits its debug port from the environment. --port 11001 selects a port for the current CLI process but does not rewrite the launched editor’s environment. Global flags may appear before or after the tool name.

Command structure

ge <tool> [--flag value ...]
ge <tool> '{"key":"value"}'
ge <tool> --help
ge help <tool>
ge list [--json]
ge raw <method> ['{...}']
ge batch

Tool names use snake_case. A kebab-case command spelling is also accepted:

ge get_editor_state
ge get-editor-state

Run ge --help for generated overview help and ge <tool> --help for the exact, current parameters of one tool. Help is generated from the same schemas published to MCP clients, so it is the authoritative parameter reference.

Parameters

The CLI derives flags and their types from each tool’s JSON schema. Schema keys are shown as kebab-case flags, while the original camelCase form remains accepted.

Scalars and enums

ge get_log --count 50 --min-level warning
ge capture_resource --name SceneView.Depth --range-min 0 --range-max 1

Numbers must be finite numbers. Enum values must match one of the choices printed by the tool’s help.

Booleans

All of these forms are supported:

ge set_gizmos_visibility --all
ge set_gizmos_visibility --no-all
ge set_gizmos_visibility --all=false
ge set_gizmos_visibility --all true

Accepted true values are true, 1, yes, and on. Accepted false values are false, 0, no, and off.

Omission is distinct from false. For example, an omitted field in set_gizmos_visibility preserves the current value.

Vectors

Vectors accept positional comma-separated values. Object-shaped vectors also accept a JSON object, including partial objects when the tool permits omitted axes:

ge set_camera --position 70,9,50 --yaw-deg 300
ge create_entity --position '{"y":9}'

Tuple-shaped parameters such as set_camera --position require every component.

Lists

Lists may be comma-separated, repeated, or supplied as JSON:

ge launch_editor --extra-args first --extra-args second
ge launch_editor --extra-args first,second
ge launch_editor --extra-args '["first","second"]'

The exact option names and element types vary by tool.

Maps and component values

Free-form objects accept repeatable key=value pairs or JSON:

ge set_component --entity-id 42 --component Light --values Intensity=3 --values Enabled=true
ge set_component --entity-id 42 --component Light --values '{"Intensity":3,"Enabled":true}'

Unquoted key=value values are converted to booleans or numbers where the schema allows typed values. Graph parameter maps that explicitly require strings preserve their values as strings.

Complete JSON parameter object

A single JSON object can replace all flags:

ge get_log '{"count":50,"minLevel":"warning"}'

The JSON object must be the only parameter argument. Quote it so the shell passes it as one token.

Validate without executing

Use --dry-run to check spelling, conversion, required values, and the final IPC method without contacting the editor:

ge set_camera --position 1,2,3 --dry-run

Example output:

{
  "tool": "set_camera",
  "ipcMethod": null,
  "params": {
    "position": [1, 2, 3]
  }
}

Output

By default, a tool prints its human-readable summary when it supplies one. Otherwise, it prints pretty-formatted JSON data.

With --json, typed and raw calls emit a one-line envelope suitable for scripts:

{"ok":true,"tool":"get_editor_state","data":{...}}

Failures also use stdout in JSON mode:

{"ok":false,"tool":"get_editor_state","code":"EDITOR_UNREACHABLE","error":"..."}

Build/rebuild chatter and nonessential progress notes are written to stderr.

Screenshot and resource-capture PNGs are never printed as base64. The CLI writes the PNG to the path reported by the editor, or to a generated capture_<time>_<sequence>.png path, and reports savedTo.

Prefer shutting down one known editor through its own debug port:

Raw debug-server calls

raw forwards a method and one JSON object directly to the editor without schema validation:

ge raw get_asset_list '{}'
ge raw open_scene '{"path":"Assets/Scenes/Main.scene"}'
ge raw physics_raycast '{"origin":[0,10,0],"direction":[0,-1,0]}'

Use raw mode when a debug-server handler has not yet been promoted to a typed tool. Run either command below to discover the current raw surface and its documentation:

ge list_debug_methods
node Tools/ai/ipc-method-drift.mjs --list

Raw calls accept zero parameters or exactly one quoted JSON object. They honor the connection flags, --json, and --dry-run.

Batch mode

ge batch sends many raw debug-server requests over one TCP connection. It reads one JSON object per nonempty stdin line:

{"method":"get_editor_state","params":{}}
{"method":"get_log","params":{"count":20}}
{"method":"take_screenshot","params":{"target":"viewport"}}

Example:

printf '%s\n' \
  '{"method":"get_editor_state","params":{}}' \
  '{"method":"get_log","params":{"count":20}}' \
  | ge batch

Important batch semantics:

  • Batch calls raw debug-server methods. Host-side tools such as build_engine, run_tests, and launch_editor cannot run through this protocol.
  • The CLI assigns string request IDs "1", "2", and so on in stdin order. An id supplied in the input object is ignored.
  • Responses can arrive out of order. Pair each response with the assigned id rather than assuming output line order matches input line order.
  • Deferred screenshots and resource captures commonly answer after faster requests.
  • The process exits after stdin closes and every sent request has received a response.
  • Empty lines are ignored. Malformed JSON lines are reported to stderr and skipped.
  • The timeout watchdog runs only while requests are outstanding; the producer may idle between requests indefinitely.

As in typed and raw mode, embedded PNG data is written to disk and replaced with a savedTo path.

Exit status

StatusMeaning
0Success.
1The tool or editor handler ran and failed.
2Invalid command-line usage or parameters.
3The editor was unreachable or closed the connection.
4A request timed out.

Shell automation should check the exit status even when parsing JSON output.

The JSON error codes are:

  • BAD_ARGUMENT
  • EDITOR_UNREACHABLE
  • EDITOR_TIMEOUT
  • TOOL_FAILED

Common workflows

Inspect the current editor

ge get_editor_state
ge get_scene_hierarchy
ge get_log --count 100 --min-level warning

The session object returned by get_editor_state identifies the worktree, branch at launch, build configuration, and optional session label. Use the worktree path—not the possibly stale branch-at-launch label—as the durable identity of an editor session.

Create and inspect an entity

ge create_entity --name InspectionLight --components '{"Light":{"Type":1,"Intensity":3}}'
ge query_ecs --has-component Light
ge get_entity_components --entity-id <id>

Use ge create_entity --help to confirm the current component-map spelling before scripting this flow.

Capture a clean viewport image

ge set_gizmos_visibility --no-all
ge take_screenshot --target viewport

Call set_gizmos_visibility with no flags to query the current state. Restore the previous state after an automated capture when sharing an interactive editor session.

Inspect a render-graph problem

ge get_render_graph_overview
ge get_render_graph_validation
ge get_render_graph_passes --include-accesses
ge get_render_graph_resources
ge get_render_graph_pass_detail --pass-name <pass-name>

Use capture_resource only after discovering the current resource name and format.

Run a build-launch verification cycle

ge editor_full_cycle
ge get_editor_state
ge get_log --count 100 --min-level warning

When several editor sessions are running, prefer explicit ports and avoid the machine-wide shutdown_editor command.

Script safely with JSON

if state=$(ge get_editor_state --json); then
  printf '%s\n' "$state"
else
  status=$?
  printf 'get_editor_state failed with status %s\n' "$status" >&2
fi

--json keeps stdout machine-readable. Diagnostic and build messages remain on stderr.

Safety and persistence

The CLI is a privileged local development interface. It can modify scenes and project files, change persisted rendering settings, build and execute code, and terminate editor processes.

Before automating mutations:

  • Confirm the target editor with get_editor_state, including session.worktreePath.
  • Pass --port for worktree-specific or benchmark editors.
  • Use --dry-run for argument validation.
  • Save or commit project files before bulk scene, ECS, or graph changes.
  • Treat set_msaa, set_aa_mode, set_taa_render_scale, and set_hdr_output as project configuration changes rather than temporary experiments.
  • Treat shutdown_editor as a machine-wide operation.
  • Use raw methods cautiously because their parameters are not schema-validated.

The debug server and host-side tools have broad access to the editor, compiler, and checkout. Do not expose the port to untrusted networks or run the CLI against untrusted projects.

Troubleshooting

Editor is unreachable

Confirm that the editor is running and that the selected port matches its debug server:

ge wait_for_editor --port 9999
ge get_editor_state --port 9999

For worktree or benchmark sessions, inspect the launch configuration and use the session-specific port.

Request timed out

Heavy screenshots and GPU readbacks can legitimately take several frames. Increase the watchdog for the invocation:

ge capture_resource --name SceneView.Color --timeout 60000

A native operating-system modal can stall the editor debug server. Prefer the scriptable open_context_menu and respond_modal paths for automation.

Development CLI output is missing or stale

Force a rebuild:

GE_CLI_FORCE_BUILD=1 node Tools/ai/ge.mjs --help

If dependencies or build output are missing:

npm --prefix mcp ci
npm --prefix mcp run build

Do not set GE_CLI_NO_BUILD=1 during normal tool development unless another build step has already produced mcp/dist.

A typed tool does not exist for a debug method

Inspect the raw-only surface:

ge list_debug_methods
node Tools/ai/ipc-method-drift.mjs --list

Then call the method with ge raw. Prefer typed tools in reusable scripts because they validate inputs and provide generated help.

Keeping the manual current

The executable registry remains the source of truth:

ge list --json
ge <tool> --help
node Tools/ai/ipc-method-drift.mjs --list

When adding a typed tool, update the relevant reference table and examples in this manual. When promoting a raw-only method, remove it from the raw appendix. The EditorIpcMethodDrift test enforces code-level coverage between C++ handlers and the typed/raw registries, while this manual provides the operator-oriented explanation.
